# Bots 3: MCP Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An owner connects an MCP client such as Claude Code to Chess Goat with their owner token. Through it they can create and manage bots, put them in groups, and play as them: reading the inbox (with waiting), reading games, moving, setting premove trees, handling challenges and draws, and challenging other bots. This covers milestone "Bots 3: MCP server", issues #102–#108, and finishes #93.

**Architecture:**
- **One endpoint.** `/mcp` is mounted on the existing Hono app, outside `/api` and its session middleware. It is served by `@modelcontextprotocol/server` v2's `createMcpHandler`, stateless, in `responseMode: 'sse'`.
- **Auth.** Our own bearer middleware resolves the owner token with `resolveOwnerToken` and passes `authInfo` into the handler.
- **Tool modules.** Each tool is a thin adapter over the existing domain functions (milestones 1 and 2). It resolves the `bot` argument to one of the owner's own bots with `requireOwnBot`, calls the domain as that bot's user id, and renders a compact, readable result.
- **Inbox.** It is derived from database state (pending challenges, games where it's the bot's turn, draw offers), so events can't be lost between calls. Waiting re-reads the inbox every 2 s and sends a progress notification every 5 s, up to `wait_seconds`.

**Tech Stack:** TypeScript, Node 22, Hono, `@modelcontextprotocol/server` ^2.4 (MCP spec 2026-07-28, with stateless 2025-11-25 fallback), zod 4, drizzle-orm, chess.js, vitest. The SDK's own client package is `@modelcontextprotocol/client`; use it in tests if it's convenient, otherwise post JSON-RPC directly.

**Spec:** `docs/superpowers/specs/2026-11-03-bot-accounts-design.md`, §1 (tokens; "can never act as the owner") and §7 (the MCP server). The notes and test-run results on #102, #103 and #105 are part of the requirements and are summarised below.

## Global Constraints

- **A token can act as the owner's bots, never as the owner.** Every play tool resolves `bot` to a live bot owned by the token's owner, using `requireOwnBot`, and calls domain code with **that bot's** user id. No tool calls domain code with the owner's id, except management tools that act on the owner's own bots, and `list_my_groups`.
- **`/mcp` auth:**
  - A missing, malformed or unknown token gives HTTP **401** with `WWW-Authenticate: Bearer`.
  - The token is never logged or echoed back.
  - Session JWTs are refused.
  - `/mcp` is not under `/api`, so session middleware never sees it, and owner tokens still work nowhere else.
- **Limits:**
  - Request body at most **512 KB** on `/mcp`.
  - **120** tool calls per minute per token.
  - At most **2** concurrent `get_inbox` waits per token. A third gets an error telling the agent to wait for its earlier call.
  - `wait_seconds` is 0–**45**.
  - **8,000** pairs per premove tree, and at most **218** children at any node.
- **SDK usage:**
  - `createMcpHandler(factory, { responseMode: 'sse' })`. Never `'json'`, which drops progress notifications.
  - A deterministic tool order.
  - Every tool has an `outputSchema`, returns `structuredContent` plus a text rendering, and has annotations: `readOnlyHint: true` on reads, `destructiveHint: true` on `delete_bot` and on `game_action` (for resign and abort).
- **Waiting:** while waiting, `get_inbox` sends `notifications/progress` every **5 s** whenever the request carries a `progressToken`, starting within 5 s. It re-reads the inbox every **2 s**, returns as soon as it's non-empty, and stops when the request's abort signal fires.
- **Activity:** every tool call naming a bot calls `touchBotActivity(tx, botId)`. Calls without a `bot` argument touch every bot the call reads (`get_inbox` with no `bot`).
- **Transactions:** `createBot` and `updateBot` run inside `db.transaction`. `bot_name_taken` propagates out of the transaction; it's never caught and continued inside it.
- **Identifiers the agent sees:**
  - bots by **name** (case-insensitive) or numeric id;
  - groups, games and challenges by their existing **public ids**;
  - people only by display name, never by Telegram id or username.
- **Errors:** a `DomainError` becomes a tool error result (`isError: true`) whose text says what to do next. For example, `stale_state` gives "The position has changed; it is now ply {ply}. Call get_game and choose again." Unexpected errors give a generic message and are logged with ids only.
- **Premoves from MCP:**
  - Moves are UCI (`/^[a-h][1-8][a-h][1-8][qrbn]?$/`).
  - Tree shape: `{ move, reply, children }`, matching `PremoveNode`.
  - On submit, check **shape only**: well-formed UCI, unique `move` among siblings, at most 218 children per node, at most 8,000 pairs. Never check legality on submit.
  - An illegal reply discovered when the tree fires discards the tree from that point, and the bot's inbox entry for that game says which reply failed.
- **Run commands with Node on PATH:** `export PATH=$HOME/.nvm/versions/node/v22.23.4/bin:$PATH`. Postgres must be running on 54329. Single file: `cd apps/<pkg> && pnpm exec vitest run <file>`. Before each commit, at the root: `pnpm lint`, `pnpm format:check`, `pnpm typecheck`. Generated drizzle output gets `prettier --write`.

## Review Focus

1. **An agent names someone else's bot, a deleted bot, or the owner themself as `bot`.** Every tool refuses with `bot_not_found` and does nothing. Test in Task 2, and in every tool's test file.
2. **An agent retries `make_move` after a dropped connection.** The same move is played at most once, and the retry returns the current state rather than an error. A different move with a stale `expected_ply` is refused with the "position has changed" guidance. Test in Task 4.
3. **An agent waits on the inbox while its bot's opponent moves.** The wait returns within about 2 s of the move. With no event, it returns after `wait_seconds` with an empty inbox, and progress notifications keep the stream alive past 60 s of client time. Test in Task 5.
4. **A premove tree whose reply is illegal in the position it reaches.** It's accepted on submit, then discarded when it fires. The inbox entry names the failing reply, and the bot is to move. Test in Task 7.
5. **A token is pasted with a trailing newline, sent as `Bearer  cgbot_…` with double spaces, or sent to `/api/...`.** `/mcp` accepts the first two, because resolve trims. `/api` refuses it as a session. Test in Task 1.

### Task 5: `get_inbox` with waiting

**Files:**
- Create: `apps/server/src/mcp/tools/inbox.ts` and `apps/server/src/domain/botInbox.ts` (`loadInbox(tx, botIds: number[]): Promise<InboxEntry[]>`)
- Test: `apps/server/test/integration/mcp-inbox.test.ts`

**Interfaces:**
- **`InboxEntry`** is one of:
  - `{ kind: 'challenge', bot, challengeId, from: { name, isBot }, group: { groupId, title }, timePerMove, rated, colour, expiresAt }`. Pending challenges **to** the bot. Challenges the bot sent are left out.
  - `{ kind: 'your_move', bot, gameId, opponent, ply, deadlineAt, drawOffer, premoveFailed?: { opponentMove, reply } }`.
  - `{ kind: 'draw_offer', bot, gameId, opponent, ply }`. Only when it's not the bot's move. On the bot's move the offer appears in `your_move.drawOffer`.
  - Ordered by deadline (soonest first; null deadlines last), then by age.
- **`get_inbox({ bot?, wait_seconds?: 0–45 })`** → `{ entries: InboxEntry[], waitedSeconds: number }`.
  - With no `bot`, it covers all the owner's live bots.
  - With `wait_seconds > 0` and an empty inbox, it re-reads every 2 s, sends progress every 5 s (when a `progressToken` is present), and returns as soon as entries appear, when the time runs out, or when the abort signal fires.
  - It touches the activity of every bot it covers.
  - The concurrency cap is enforced per token (Global Constraints).
